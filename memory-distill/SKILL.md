# Memory Distill

从碎片化、不连续的人机协作过程中，提炼少量真正有长期价值的工程经验，并沉淀到 Experience 库。

Memory Distill 不保存对话记录，而是将已经形成的结论、方法、决策和实践整理为可复用的工程经验。

## 使用场景

当当前工作已经形成对未来有参考或复用价值的内容时，可以执行 Memory Distill，例如：

- 已解决的问题及其有效处理方式
- 已确认的判断、选择或取舍
- 经过验证的方法或可复用规律
- 长期稳定的偏好、条件或限制

用户可以主动要求沉淀，Agent 也可以检查当前工作是否产生了值得保存的 Experience。

## 核心原则

Memory Distill 不记录完整的工作过程，而是从中提炼未来仍然有用的 Experience。

Experience 应基于已经确认的内容，脱离原始上下文后仍能理解，并能够帮助未来更快作出判断、复用已有做法或减少重复探索。

沉淀时只保留正确理解和复用所需的信息，不追求内容完整或记录数量。具体的准入、表达和处理方式按照 `memory-policy.md` 执行。

没有符合条件的内容时，不修改 Experience 库，也不为完成沉淀而强行生成 Experience。

## 两种模式

### 默认模式：当前会话

只从当前对话窗口中已有的内容提取经验。不读取任何外部文件，不扫描历史会话。

适用于日常工作中随时沉淀经验。

### 项目模式：全量历史会话

当用户明确要求时（如"提取项目所有会话"、"扫描历史会话"、"项目级提取"），扫描该项目的所有历史会话。

执行前必须先确认：用户是否明确要求了项目级提取？如果没有，只使用默认模式。

## 默认模式

默认模式只处理当前 Agent 已经获得的内容，不主动读取历史内容，也不读取或更新 `scan-state.json`。

### 1. 发现候选 Experience

从当前工作内容中识别已经形成明确结论、判断、做法或限制的信息。尚在讨论、等待确认或仅用于当前过程的内容，不作为候选 Experience。

### 2. 提炼 Experience

将候选内容整理为脱离原始上下文后仍能独立理解和复用的 Experience。一条 Experience 只表达一个独立结论，具体表达方式按照 `memory-policy.md` 执行。

### 3. 判断是否保存

按照 `memory-policy.md` 判断候选 Experience 是否满足准入条件，并确定其类型。不满足条件的内容直接跳过，不修改 Experience 库。

### 4. 确定 Space 并检查已有 Experience

按照 `storage.md` 逐条判断候选 Experience 所属的 Space，并读取该 Space 的相关内容。将候选 Experience 与已有 Experience 比较，再按照 `memory-policy.md` 决定新增、更新、替代或跳过。

### 5. 保存 Experience

按照 `storage.md` 定义的格式和写入规则保存 Experience，并同步更新必要的索引信息。只修改目标 Space 和相关索引，不修改无关内容。没有需要保存的 Experience 时，不对 Experience 库作任何修改。

## 项目模式

仅在用户明确要求提取项目历史内容时执行。默认模式只处理当前已经获得的内容，不读取或更新 `scan-state.json`。

### 1. 收集历史内容

从当前环境能够访问的历史来源中，收集与目标项目相关的内容。具体访问方式由当前 Agent 或平台根据已有能力决定，不主动访问未授权或无法获取的来源。历史内容只作为候选输入，不直接视为 Experience。

### 2. 增量扫描

在 Experience 根目录维护 `scan-state.json`，记录各个历史来源已经处理到的位置，避免重复扫描：

```json
{
  "sources": {
    "workspace:agent-design": {
      "checkpoint": "2026-07-13T10:00:00+08:00"
    }
  }
}
```

来源标识应能够稳定定位对应内容。`checkpoint` 可以是时间、游标、版本号或其他进度标识，具体形式由历史来源决定。

扫描时只读取 `checkpoint` 之后新增或发生变化的内容。内容量较大时，可以先读取摘要或元数据，再按需获取相关的完整内容。只有本次扫描、提炼和保存全部完成后，才更新对应的 `checkpoint`。执行失败或中断时保持原值，避免遗漏。

`scan-state.json` 只记录扫描进度，不参与 Experience 的价值判断、Space 归属和索引定位，也不得用于恢复已经删除的内容。

### 3. 进入提炼流程

收集到的历史内容统一进入正常提炼流程，按照默认模式完成发现、提炼、判断、检查和保存。

是否形成 Experience 由 `memory-policy.md` 判断，具体存储方式按照 `storage.md` 执行。

每条 Experience 仍需根据自身主题独立判断所属 Space，不按照历史来源或项目名称直接归类。

## 输出结果

完成后简要说明本次处理结果：

```text
Memory Distill 完成

新增：2  更新：1  替代：0  跳过：3
涉及 Space：agent-design、software-engineering
```

项目模式可以补充历史内容处理情况：

```text
历史内容：读取 2 个来源，处理 8 条增量内容，扫描进度已更新。
```

跳过项只有在原因需要用户关注时才单独说明，不必逐条罗列普通重复内容。

没有发现值得沉淀的内容时：

```text
本次未发现适合长期沉淀的 Experience，Experience 库未发生变化。
```
