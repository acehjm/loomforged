# AI、整体可行性与 PoC

完成场景定界和业务闭环后，按用户问题选择本文件中的相应部分。AI 是候选控制手段之一；优先选择复杂度最低、能可靠控制风险的组合。

## AI 适用性

依次检查六个门槛：

| 门槛 | 核心问题 |
|---|---|
| 可观察 | 事件是否留下稳定、及时且足够清晰的信号？ |
| 可定义 | 不同业务人员能否一致区分事件、授权和例外？ |
| 有数据 | 是否有覆盖真实环境、负样本和长尾情况的数据？ |
| 可承错 | 误报、漏报、时延和不可用的后果是否可管理？ |
| 可行动 | 结果是否对应责任人、处置动作和有效时间窗？ |
| 可运营 | 谁维护规则、处理反馈、监测漂移并负责回滚？ |

任何决定性门槛不成立时，将 AI 判断为 `当前不建议`；存在可补齐缺口时判断为 `有条件适合`；门槛基本成立且主要风险有控制时判断为 `适合`。不使用加权总分抵消否决项。

把光照、遮挡、角度、距离、密度、天气、噪声、弱网和设备故障纳入可观察性。高后果场景配置人工复核、多信号验证、规则校验或物理防护等独立控制。没有现场数据时只定义指标和测量方式，不承诺准确率。

比较 AI 与流程调整、培训、物理隔离、门禁联锁、普通传感器、规则告警和人工巡检。只有识别结果能够进入业务闭环时，AI 才产生业务价值。

## 整体可行性

按需评估以下维度，逐项给出证据、缺口、前置条件和置信度：

| 维度 | 核心问题 |
|---|---|
| 业务 | 问题是否重要、可定义且有业务所有者？ |
| 治理 | 政策、权限、数据和责任条件是否成立？ |
| 工程 | 感知、供电、网络、安装和环境是否支持？ |
| 数据/AI | 事件、样本、错误成本和持续运营是否可管理？ |
| 集成 | 事件和数据能否进入现有系统与流程？ |
| 运营 | 是否有人持续核实、处置、维护和复盘？ |
| 经济 | 全生命周期成本是否匹配可量化价值？ |
| 实施 | 周期、依赖和组织变更是否可控？ |

结论使用：

- `可直接推进`：关键条件已具备。
- `满足条件后推进`：方向成立，但有明确前置事项。
- `先做 PoC`：核心不确定性可通过有限试验验证。
- `当前不建议`：存在不可观察、不可治理、无法闭环或成本失衡等根本问题。

同时标记置信度。单独列出否决项，不用综合分数隐藏。没有可靠数据或报价时只分析成本构成和测量方法，不虚构金额、节省人数或事故降幅。

## PoC

先写业务假设：

> 如果在【代表性场景】获得【能力】，并由【角色】按【流程】处置，那么【业务指标】应相对【当前基线】产生【可观察变化】。

PoC 至少确定：

1. 代表性区域、困难区域、时段、对象和边界条件。
2. 正样本、负样本、相似干扰、例外和故障状态。
3. 当前事件量、发现方式、处置时长和人工投入基线。
4. 模型、系统、流程和业务四层指标。
5. 通过、整改、停止的门槛及争议复核方式。
6. 参与角色、数据责任、观察周期和退出安排。

常用指标：召回率、精确率、每路每日误报数、端到端时延、在线率、有效告警率、确认时间、处置及时率、闭环率、重复事件和人工负担变化。根据风险后果与运营承载能力设门槛，高风险低频事件单独观察。

采用渐进路径：场景与基线调查 → 离线样本验证 → 受控现场 PoC → 有限试运行 → 决定扩展、调整或停止。

**完成条件**：AI 结论对应六个门槛；整体可行性逐项呈现否决项和前置条件；需要 PoC 时已定义业务假设、基线、指标和决策门。
