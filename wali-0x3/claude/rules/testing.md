# 测试规则

- 独立验证只在 `phase: inspecting`、活动任务处于 `review` 且 `carried_changes` 指纹未变化时运行 Goal 已声明的检查命令，不修改实现或测试文件。需要新增测试代码时，建立关联 AC 的实施任务并转入 `implementing`。
- `spec.md` 的验收判定规则是测试 oracle；每个场景都要能追溯到 Requirement、AC 和 Task，发现缺失、歧义或不可判定条款时记录问题并回到澄清，而不是由 Tester 临时发明规则。
- 测试模板、依赖兼容信息和外部接口样例从 Spec/Task 引用的项目 `docs` 来源读取；只有 `refs/INDEX.md` 明确路由给 Tester 的跨项目资料才加载。两者都不能替代 Rule 或 Spec 的判定条件。
- 测试描述可观察行为，不依赖实现细节；一个失败应尽量指向一个明确原因。
- 覆盖正常路径、主要失败路径、边界值以及本次修改可能影响的回归路径。
- Bug 修复应先建立可失败的复现或等价证据，再验证修复前失败、修复后通过。
- 测试必须确定、隔离并可重复；控制时间、随机数、网络和共享状态，不用盲目重试掩盖不稳定。
- 不删除、跳过、放宽断言或过度 Mock 来迁就实现。确需调整测试契约时，先证明原契约与目标冲突。
- 记录精确命令、退出码、结果摘要、环境和未覆盖范围；不要只写“测试通过”。
- 工作图解析、依赖、阻断和并行判断必须以公开 CLI 行为测试覆盖，避免只测内部函数。
