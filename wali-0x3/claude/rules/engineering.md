# 工程实现规则

- 只在 `phase: implementing`、Goal 已确认且 `active_task` 有效时修改代码。只有 `@active_task` 从任务“允许修改范围”解析出的项目相对路径可写。
- 实现同时受 `spec.md` 的 Requirement、行为、接口、数据、错误和质量约束；Goal 摘要与 Spec 冲突时停止并交还 Coordinator 澄清，不自行挑选有利解释。
- 修改前先读取相关入口、调用方、测试和仓库已有规范；遵循现有架构与命名，不创造平行惯例。
- 只读取 Spec 或活动任务关联的项目 Refs；模板和示例是按版本选择的参考，不是复制即正确。硬性依赖、禁用库和强制模板以适用 Rule 为准，本 Goal 的具体选择以 Spec 为准。
- 实现满足验收条件的最小完整方案，避免未被当前需求证明的抽象、配置和依赖。
- 保持接口、数据迁移和行为兼容；有意的破坏性变化必须在目标契约中明确并获确认。
- 显式处理输入验证、错误传播、资源清理、并发边界和安全敏感数据。
- 不提交秘密、凭据、个人路径、临时日志、调试开关或无关生成物。
- 不用类型逃逸、空异常处理、关闭规则或降低校验标准掩盖失败；必要例外要最小化并记录理由。
- 每个增量完成后检查 `svn diff --internal-diff`，运行最小相关验证，再根据影响范围扩大验证。
- 实现转入 `inspecting` 前运行 `wali_policy.py carry`，冻结本轮合法实现差异的内容与 SVN 属性指纹；不得在检查阶段继续改动再补写指纹。
- 项目命令必须与 `goal.md` 检查表中的完整命令一致。命令或其调用能力产生的新文件仍必须在活动任务范围内，不将生成物默认视为项目资产。
- 本地项目命令及其加载的脚本、插件和依赖属于可信计算基础；来源或传递代码不可信时不得本地运行，改由用户在隔离环境或 CI 执行并提供证据。WALI 的本地快照是审计证据，不是 OS 级防篡改沙箱。
- 只修改任务在工作图中声明的范围；范围含糊或与其他 working 任务重叠时，先由 Coordinator 收窄或重新排期。
- 普通任务不得声明项目根级通配范围，也不得修改 `.claude/**`、存档形态的 `claude/**` 或 `CLAUDE.md` 控制面。
- SVN 调度和同步同样受活动任务范围约束：只对精确 leaf path 使用允许的 `add/delete/move/copy/update/resolve --accept working` 形式。交付前若需更新或解决冲突，返回 `implementing`，核对合并、重新测试并刷新 `carry`；提交授权本身不包含这些操作。
