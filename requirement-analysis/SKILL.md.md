# Security Requirement Review

将客户提供的需求材料整理为清晰、可评审、可继续传递给售前、产品和研发人员的需求清单。

## 使用场景

当用户提供以下内容，并希望进行需求整理、分析或初步评估时使用：

- 客户需求说明
- 招标文件或技术参数
- 售前交流记录
- 项目会议记录
- 现场调研记录
- 功能清单
- 零散需求描述
- 客户反馈或补充要求

适用于煤炭化工、高校、文旅及其他安防软件项目。

本 SKILL 只负责需求整理和初步评审，不直接生成完整解决方案、研发排期或项目报价。

## 输入要求

用户应至少提供一种需求材料。

可选补充信息包括：

- 项目名称
- 客户行业
- 建设背景
- 已有系统
- 公司产品资料
- 接口或设备资料
- 已确认的项目边界
- 历史项目资料

输入信息不完整时，继续完成能够确认的部分，并将缺失信息列入待确认事项。

## 处理原则

### 忠实原始材料

- 保留全部有效需求，不遗漏明确内容。
- 不改变客户原意。
- 不将推测内容写成客户明确要求。
- 不因表述重复而删除其中存在的差异。
- 原始材料存在矛盾时，应明确指出，不自行选择其中一个结论。

### 需求与分析分离

每条需求应区分：

- 客户原始要求
- 对需求的整理说明
- 初步支持判断
- 判断依据
- 待确认内容

不得将分析结论混入客户原始需求。

### 信息不足不强行判断

当缺少产品资料、接口资料、设备信息或项目范围时，应标记为“信息不足”。

不得仅根据行业经验判断公司产品已经支持某项功能。

### 行业知识只用于辅助理解

可以使用安防行业及客户行业常识帮助理解术语、场景和业务关系，但不得：

- 将行业常见做法当作客户明确需求
- 根据行业经验擅自扩大项目范围
- 虚构法律法规、标准或验收要求
- 将其他项目的做法直接套用到当前项目

## 执行流程

### 1. 识别项目背景

从输入材料中识别：

- 客户行业
- 建设目标
- 主要使用对象
- 涉及的业务区域
- 已有系统或建设基础
- 本次项目的大致范围

无法确认的内容不补充，统一列入待确认事项。

### 2. 识别业务范围

识别需求可能涉及的业务领域，例如：

- 视频监控
- 门禁管理
- 访客管理
- 车辆管理
- 报警管理
- 周界防范
- 智能分析
- 地图展示
- 应急指挥
- 设备管理
- 系统集成
- 数据交换
- 用户与权限
- 运维管理
- 移动端应用
- 部署与安全

仅根据实际输入识别，不要求覆盖全部领域。

### 3. 拆分独立需求

将原始材料拆分为可单独评审的需求项。

每条需求应尽量只表达一个主要目标。

以下情况通常需要拆分：

- 一句话包含多个独立功能
- 一个要求涉及不同使用对象
- 一个要求包含功能和性能两个方面
- 一个要求包含建设内容和验收条件
- 一个要求同时涉及多个系统
- 不同部分需要由不同团队实现

以下情况不宜过度拆分：

- 同一业务动作的必要步骤
- 无法独立交付的连续流程
- 拆分后会失去完整业务含义的规则
- 仅为同一功能补充说明的内容

需求编号统一使用：

```text
R-001
R-002
R-003
```

编号按照需求在输出中的出现顺序连续生成。

### 4. 完善需求说明

在不改变原意的前提下，说明每条需求的：

- 业务目的
- 使用对象
- 涉及系统
- 输入和输出
- 主要处理过程
- 关键限制
- 已明确的验收要求

仅填写原始材料能够支持的内容。

### 5. 进行初步支持判断

每条需求只能使用以下一种初步判断。

#### 已支持

已有明确产品资料、版本说明、系统现状或用户提供的证据证明当前能力可以直接满足。

判断为“已支持”时，必须写明依据。

#### 需要配置

现有产品具备相关能力，但需要通过参数、规则、流程、权限、模板或界面配置完成。

不得把代码开发描述为配置。

#### 需要定制开发

现有能力无法直接满足，需要新增或修改软件功能、接口、流程、页面、报表、算法或数据处理逻辑。

当前无法确定开发范围时，应同时列出待确认事项。

#### 需要第三方配合

需求实现依赖外部厂商、已有平台、硬件设备、接口开放、数据提供或其他非本项目团队可以独立完成的条件。

应说明依赖的第三方及配合内容。

#### 信息不足

缺少足够信息，无法判断是否支持或采用何种实现方式。

以下情况通常应判断为“信息不足”：

- 未提供公司产品资料
- 未说明现有系统情况
- 接口协议不明确
- 设备型号或能力不明确
- 业务流程未确认
- 数据来源不明确
- 项目边界不明确
- 性能规模不明确
- 客户表述存在矛盾

没有产品能力依据时，不得判断为“已支持”。

### 6. 汇总待确认事项和风险

将各需求中的待确认内容合并整理。

待确认事项应尽量写成可直接向客户、产品或研发人员提出的问题。

风险提示只基于输入材料和分析结果，包括但不限于：

- 项目范围不明确
- 系统边界不明确
- 接口依赖未确认
- 第三方配合存在不确定性
- 性能指标缺少规模依据
- 验收标准不明确
- 客户要求存在冲突
- 产品能力缺少依据
- 需求可能涉及定制开发
- 数据安全或权限边界未确认
- 部署环境存在不确定性

不得为了显得完整而虚构风险。

## 需求整理规则

### 保留原始需求

“原始需求”应尽量保留客户原始表述。

可以进行以下处理：

- 修正明显的排版问题
- 合并完全重复的句子
- 补全明确的指代对象
- 去除不影响含义的口语表达

不得对原始需求进行方案化改写。

### 需求名称

需求名称应简洁表达核心目标。

例如：

```text
访客预约登记
重点区域越界报警
视频平台统一接入
多校区权限管理
客流数据统计
```

避免使用以下模糊名称：

```text
功能要求
系统建设
平台需求
其他功能
相关能力
```

### 判断依据

判断依据应说明结论来自哪里，例如：

- 用户提供的产品功能清单
- 当前系统已经具备
- 产品版本说明中已明确支持
- 需求明确要求新增开发
- 依赖第三方平台开放接口
- 当前材料未提供相关信息

不得使用“根据经验判断”“一般可以实现”等模糊表述作为已支持依据。

### 待确认问题

待确认问题应具体、可回答。

推荐：

```text
现有门禁设备的厂商、型号和接入协议是什么？
访客信息由本系统维护，还是从统一身份平台同步？
视频保存时间是30天还是90天？
项目是否需要同时覆盖多个校区？
报警事件是否需要与广播系统联动？
```

避免：

```text
需要进一步沟通。
需要确认具体需求。
相关信息不明确。
```

## 输出要求

默认在对话中输出完整评审结果。

输出结构按照 `template.md` 执行。

输出内容包括：

1. 项目背景
2. 业务范围
3. 需求清单
4. 待确认事项
5. 风险提示

需求较多时，可以按照业务领域分组，但需求编号必须保持连续。

没有相关内容的章节应写明“当前材料未提供”，不得凭空补充。

## 限制

执行过程中不得：

- 虚构客户需求
- 虚构公司产品能力
- 擅自扩大项目范围
- 将行业经验写成客户要求
- 将历史项目能力视为当前标准产品能力
- 直接承诺开发工作量
- 直接承诺交付周期
- 直接生成项目报价
- 虚构接口能力
- 虚构法规、标准或验收条款
- 隐藏原始材料中的矛盾
- 对信息不足的需求强行给出确定结论

## 质量检查

输出前检查：

- 是否遗漏原始材料中的明确需求
- 是否每条需求只包含一个主要目标
- 是否保留了客户原始含义
- 是否区分了原始需求和分析结论
- 是否为每条需求分配了唯一编号
- 是否为每条需求给出了初步判断
- “已支持”是否具有明确依据
- 信息不足的内容是否列入待确认事项
- 待确认问题是否具体、可回答
- 是否识别了材料中的冲突和依赖
- 风险提示是否有输入依据
- 是否增加了材料中不存在的需求
- 是否擅自承诺了功能、工期或工作量

如存在漏项、无依据判断或自行补充，应修正后再输出。
