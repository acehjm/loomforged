# Industry Demand Analysis

将内部系统中的零散需求转化为可检索、可统计、可追溯的行业需求数据，并从中识别高频场景、共性业务和产品机会。

本 Skill 包含三个能力：

```text
pull      拉取并保存需求数据
classify  识别需求对应的场景和业务
report    生成行业需求分析报告
```

用户要求完整分析时，依次执行：

```text
pull → classify → report
```

已有可用的本地数据时，从对应阶段继续，不重复拉取或处理。

确定性工作由脚本完成，包括接口请求、分页、去重、统计和文件生成；模型负责需求理解、场景识别、业务归纳和报告解读。

## 任务判断

根据用户意图选择执行阶段：

- 指定行业、时间范围、需求编号或项目条件时，执行 `pull`。
- 提供一条需求并要求识别场景或业务时，执行 `classify`。
- 要求分析行业趋势、高频需求、产品分布或高价值需求时，执行 `report`。
- 要求生成完整行业需求报告时，依次执行全部阶段。

不要在缺少本地需求数据时直接生成统计报告，也不要将一次单条需求识别扩展为完整行业分析。

## Pull：拉取需求数据

根据用户指定的行业、时间范围或其他查询条件，调用本地数据脚本，从内部需求系统获取需求。

输入条件可以包括：

- 行业。
- 开始时间和结束时间。
- 用户明确指定的其他查询条件。

执行流程：

1. 从本地环境变量或私有配置读取接口地址和 Cookie。
2. 调用需求查询接口并获取全部分页数据。
3. 删除完全重复的记录，保留需求原文和后续分析需要的字段。
4. 将处理后的数据保存到本地。
5. 返回查询范围、需求数量和文件位置。

至少生成：

```text
data/<行业>/<时间范围>/
├── requirements.jsonl
└── requirements.md
```

`requirements.jsonl` 作为后续分类和统计的数据源，`requirements.md` 用于人工阅读和检查。

Markdown 中每条需求采用以下结构：

```markdown
## <需求编号>｜<项目名称>

- 行业：
- 区域：
- 产品：
- 创建时间：

### 需求内容

<原始需求文本>

### 评估内容

<评估内容文本>
```

### 安全要求

Cookie 和其他身份凭证只能从环境变量等私有配置中读取，不得写入 Skill、需求数据、日志或报告。

默认只查询内部系统，不修改、提交、审批或删除任何数据。

### 完成条件

- 已获取符合查询条件的全部分页数据。
- 已生成 `requirements.jsonl` 和 `requirements.md`。
- 已返回需求数量、查询范围和保存位置。
- 接口异常或数据不完整时，已明确说明实际获取情况。

## Classify：识别场景和业务

读取用户输入的需求，或读取本地 `requirements.jsonl`，逐条识别需求所表达的业务含义。

每条需求输出：

```
summary: 需求要解决的核心问题

scene: 需求发生的业务场景
business: 场景中开展的具体业务

objects:
  - 涉及的业务对象

products:
  - 明确关联的产品

requirement_type:
  - 需求类型

confidence: high

evidence:
  requirement:
    - 支撑判断的需求原文
  assessment:
    - 辅助判断的评估内容

inference:
  - 需求内容和评估内容均未明确表达的分析判断

questions:
  - 当前信息不足或不同评估结论存在冲突时，需要确认的问题
```

识别时按照以下顺序理解需求：

```text
提取业务对象和动作
→ 判断需求要解决的问题
→ 识别业务发生的场景
→ 归纳场景中的具体业务
→ 识别关联产品和需求类型
```

场景描述业务发生的环境和目标，例如“局校数据互联”“校园人员通行”“化工企业二道门管理”。

业务描述场景中的具体活动，例如“基础数据同步”“访客预约登记”“反三违算法识别”。

接口对接、页面开发、字段增加等属于功能或实现方式，不能直接作为业务场景。

### 使用评估内容

识别场景和业务时，以需求内容为主要依据，并结合评估内容辅助理解需求意图、产品归属和业务边界。

评估内容不作为独立的分析对象，也不需要提取为复杂的评估结构。多个评估人的结论可以共同作为分类依据；存在冲突时，应降低 `confidence`，并将分歧记录到 `questions`。

不得使用评估内容覆盖或改变原始需求。分类结果引用评估内容时，应在 `evidence.assessment` 中保留对应依据。

### 相似需求匹配

存在本地历史数据时，同时匹配语义相近的需求，说明：

- 相似需求编号和项目。
- 共同的场景、业务或业务对象。
- 两条需求的主要差异。
- 已有产品能力是否可以复用。

匹配时优先比较业务对象、业务动作和业务目标，不能仅凭关键词相同判断为同类需求。

### 分类整理

场景和业务分类保存在 `taxonomy.md`，用于统一同类需求的表达，并支持后续统计分析。

首次处理某个行业的全量需求时，先完成需求识别，再对全部分类结果进行统一整理：

- 合并含义相同或相近的场景和业务。
- 统一分类名称和表达粒度。
- 避免同一类需求因不同说法被分散统计。
- 将整理后的分类结果写入 `taxonomy.md`。

后续处理增量需求时，优先使用已有分类。无法匹配的内容可以暂时标记为候选分类，待本次增量数据处理完成后统一整理并更新。

不要在逐条识别过程中频繁修改分类体系。

### 分析边界

必须区分：

- 原始需求明确表达的内容。
- 根据原文归纳出的场景和业务。
- 基于经验推断出的内容。
- 当前无法确认的问题。

推断内容写入 `inference`，不能混入需求原文或明确的分类结果。

信息不足时降低 `confidence`，并将需要确认的内容写入 `questions`，不要为了获得完整结果而强行判断。

分析结果保存为：

```text
data/<行业>/<时间范围>/classified.jsonl
```

### 完成条件

- 每条需求均已识别场景、业务、业务对象和关联产品。
- 分类结果能够通过 `evidence` 追溯到原始需求。
- 推断内容和原始需求已经分开。
- 不确定结果已经降低置信度并记录待确认问题。
- 已生成 `classified.jsonl`。

## Report：生成行业需求分析报告

读取 `classified.jsonl`，对指定行业的全部需求进行归并和统计，提取行业中的主要场景、核心业务和高频需求，并生成 HTML 分析报告。

Report 面向整个行业数据集，不针对某个项目或单条需求展开分析。

执行时，先合并含义相同或相近的分类结果，再按照以下关系组织行业需求：

```text
行业
→ 场景
→ 业务
→ 具体需求
→ 关联产品
```

重点分析：

- 行业中包含哪些主要场景。
- 每个场景下包含哪些核心业务。
- 各场景和业务对应的需求数量。
- 各业务下反复出现的具体需求。
- 各场景和业务涉及的产品。
- 需求、场景、业务与产品之间的关系。
- 各场景和业务在不同时间段内的变化。
- 新出现或增长明显的场景和业务。

报告应回答：

1. 当前行业需求主要分布在哪些场景？
2. 每个主要场景包含哪些核心业务？
3. 哪些场景和业务出现次数最多？
4. 各业务下主要包含哪些具体需求？
5. 哪些需求在不同项目中反复出现？
6. 哪些场景或业务涉及的产品最多？
7. 哪些场景和业务正在增加、减少或新出现？
8. 从当前需求数据中，可以形成怎样的行业业务全貌？

### 高价值需求

本 Skill 中的高价值需求，是指出现次数多、涉及产品多，在行业需求中具有较高重要性的需求。

统计前应先归并含义相同或相近的需求，并删除完全重复的记录。

默认按照以下方式识别：

1. 以归并后的需求出现次数作为主要判断依据。
2. 以关联的不同产品数量作为补充判断依据。
3. 同时展示需求次数、涉及产品和所属场景，不使用无法解释的综合评分。

同一需求在不同项目中独立出现时分别计数；同一条数据的重复记录只保留一次。

### HTML 报告

生成可独立打开的 HTML 文件：

```text
reports/<行业>-<时间范围>-demand-analysis.html
```

报告一般包括：

1. 行业需求概览。
2. 核心分析结论。
3. 行业场景分布。
4. 场景与业务关系。
5. 核心业务排名。
6. 高频需求分析。
7. 产品关联分析。
8. 场景和业务变化趋势。
9. 典型需求。
10. 数据范围与分析说明。

报告应优先呈现行业场景和业务结构，产品、项目和时间作为辅助分析维度。

图表中的数量、占比、排名和趋势必须来自结构化数据统计，模型不得自行编造。

结论应能够追溯到具体需求编号、项目和原始内容。数据量较少或时间范围不完整时，应明确限定结论范围。

### 完成条件

- 已完成同义场景、业务和需求的归并。
- 已形成行业、场景、业务、需求和产品之间的关系。
- 已统计各场景和业务的需求数量。
- 已识别高频需求及其涉及产品。
- 所有统计数字均来自 `classified.jsonl`。
- 报告结论能够追溯到具体需求。
- HTML 文件可以独立打开。
