# Code Compliance Fix

检查定制项目源码的合规性问题并直接修复。

## 处理范围

仅处理以下内容：

- 错误码
- 日志
- 代码格式
- 配置
- 依赖

禁止：

- 修改业务逻辑
- 调整接口行为
- 重构代码结构
- 优化业务实现
- 修改数据库设计
- 处理上述范围之外的问题
- 将本 Skill 扩展为 Code Review

无法在不改变业务逻辑的情况下修复时，保留原代码并在结果中说明。

## 执行原则

- 默认检查整个项目源码。
- 发现问题后直接修复，无须逐项确认。
- 仅在无法获取错误码前缀时询问用户。
- 优先沿用项目已有的类、工具、配置方式和代码风格。
- 不臆造不存在的业务规则。
- 不修改生成代码、构建产物和第三方源码。
- 所有修改完成后必须重新检查。
- 依赖检查仅在用户明确要求时执行。

## 执行流程

按以下顺序执行：

1. 识别项目结构、构建方式、配置文件和打包类型。
2. 检查并修复错误码。
3. 检查并修复日志。
4. 检查并修复 Logback 配置。
5. 检查并修复生产环境配置。
6. 清理无效导入并格式化代码。
7. 按需执行依赖检查。
8. 重新执行全部已启用规则。
9. 在对话中输出简短汇总。

## 错误码

### 获取错误码前缀

从 `application.yml` 或对应配置文件读取：

```yaml
starfish:
  core:
    error-code:
      prefix: xxx
```

如果项目使用扁平配置，也应识别：

```yaml
starfish.core.error-code.prefix: xxx
```

如果没有配置：

1. 询问用户提供错误码前缀。
2. 将前缀写入项目使用的主配置文件。
3. 继续执行后续检查。

这是唯一需要主动询问用户的情况。

### 检查错误码类

检查项目中的 `*ErrorCode` 类或枚举。

错误码必须符合：

```text
{error-code-prefix}{5位数字}
```

同时满足：

- 数字部分固定为五位。
- 同一错误码类中的数字按顺序递增。
- 错误码不能重复。
- 枚举常量名称必须以 `ERR_` 开头。

修复规则：

- 保留已经合法且不重复的错误码。
- 从现有最大合法序号之后继续分配新错误码。
- 修复格式错误、重复或缺失的错误码。
- 枚举名称不符合要求时进行重命名，并同步更新所有引用。
- 不改变错误码对应的业务语义。

### 检查错误码翻译

检查：

```text
_pkg/linux/language/zh_CN/translate.properties
```

`*ErrorCode` 中的每个错误码都必须存在：

```properties
errorCode.{error-code}.description=错误描述
errorCode.{error-code}.suggestion=1. 处理建议。
```

要求：

- `description` 和 `suggestion` 必须同时存在。
- `suggestion` 必须以中文句号 `。` 结尾。
- 不得出现重复键。
- 错误码发生变化时同步更新翻译键。
- 优先复用错误码类中的描述、现有翻译和异常上下文。
- 缺失内容可根据枚举名称和使用上下文补全，但不得添加代码中不存在的业务含义。

日志检查新增错误码后，必须重新执行本节规则。

## 日志

### 基本要求

日志必须满足：

- 日志内容使用英文。
- 禁止打印密码、密钥、令牌、完整认证信息等保密内容。
- 禁止打印图片 Base64、文件完整内容、超长报文或大型对象。
- 身份证号、手机号等敏感信息必须脱敏后打印。
- 脱敏后应保留必要的排查信息。
- 优先使用项目已有脱敏工具，不重复实现脱敏逻辑。
- 日志应当简洁、明确，并能够作为问题排查证据。

### 日志有效性

删除或调整以下日志：

- 没有排查价值的日志。
- 同一信息被重复打印。
- 高频循环中无必要的 `info` 日志。
- 输出整个请求、响应或大型对象的日志。
- 只打印固定文字、无法定位调用对象或执行结果的日志。
- 正常分支中数量过多、导致关键日志被淹没的日志。

补充以下关键日志：

- 异常被捕获但未记录。
- 外部系统、数据库、缓存或消息调用失败。
- 重试最终失败。
- 关键任务执行失败。
- 关键状态转换失败。
- 错误返回前缺少必要排查信息。

不要为每个方法、每个分支或每次循环机械增加日志。

### 日志等级

根据业务重要程度和调用频率选择等级：

- `error`：操作失败、异常终止、关键任务失败或需要人工关注的问题。
- `warn`：可恢复异常、降级、重试、无效外部数据或潜在风险。
- `info`：低频且重要的生命周期、任务结果或关键状态变化。
- `debug`：高频调用、内部过程和仅用于开发排查的信息。

重点修复：

- 高频代码块使用 `info` 或 `error` 输出普通过程信息。
- 正常业务分支错误使用 `error`。
- 异常失败只使用 `info` 或 `debug`。
- 同一异常在多层重复打印。

### 错误日志与错误码

所有 `error` 日志必须包含对应的 `*ErrorCode` 错误码。

标准形式示例：

```java
log.error(HikLog.toLog(errorCode, "Failed to process request"), exception);
```

如果当前失败场景没有对应错误码：

1. 在项目的 `*ErrorCode` 类中新增错误码。
2. 在日志中使用该错误码。
3. 补充对应的中英文错误码资源。
4. 重新执行错误码检查。

不得为了减少错误码数量而复用语义明显不匹配的错误码。

### 日志记录方式

必须使用项目已有的 `HikLog.toLog` `HikLog.toLogWithParam` 标准形式。

例如：

```java
log.error(HikLog.toLog(errorCode, "Failed to execute task"), exception);
log.info(HikLog.toLog("Task completed"));
```

执行时：

- 以项目中已经存在的 `HikLog.toLog`  `HikLog.toLogWithParam` 方法签名为准。
- 不得自行创造不存在的重载方法。
- 不得使用字符串拼接代替标准日志结构。
- 异常对象应作为日志方法的独立参数传入。
- 缺少关键信息时补充任务编号、请求编号、对象标识、执行阶段或结果。
- 不得为补充日志而输出敏感信息。

## Logback 配置

如果项目`resource`目录下存在 `logback.xml` 或等效配置，则进行检查。

### LOG_HOME

根据项目打包类型检查日志目录 `LOG_HOME`。

WAR 包：

```text
${catalina.base}/logs/...
```

JAR 包：

```text
${component.log.path}/logs/...
```

要求：

- 根据 `pom.xml` 配置或部署方式判断打包类型。
- 修复明显不符合打包方式的日志目录。
- 保留项目已有的日志子目录命名。

### 组件标识和段标识

配置中至少应引入：

```xml
<springProperty scope="context" name="component.id" source="component.id" />
<springProperty scope="context" name="component.segment.id" source="component.segment.id" />
```

要求：

- 沿用当前 Logback 文件已有的属性引入方式。
- 日志输出文件名中必须同时包含组件标识和段标识。
- 不随意调整 Appender、滚动策略、保留时间和日志格式。
- 除本节要求外，不重构 Logback 配置。

## 代码格式

### 无效导入

清理 Java 类中的：

- 未使用导入。
- 重复导入。
- 格式化后不再需要的导入。

不得删除通过注解处理、反射配置或框架机制实际需要的代码。

### Google Java 格式化

按照 Google Java Style 格式化 Java 代码。

执行优先级：

1. 使用项目已有的 Spotless、google-java-format 或格式化命令。
2. 使用当前环境可用的 google-java-format。
3. 编译器支持的格式化方式。
4. 无可用格式化工具时，仅进行能够安全完成的格式整理，并在结果中说明。

要求：

- 不为格式化目的新增项目依赖。
- 不修改生成代码和第三方源码。
- 格式化不得改变代码行为。
- 至少格式化本次修改涉及的全部 Java 文件。

## 生产配置

检查被**生产环境**加载的配置，一般文件命名直接以为 `application.*` 或包含 `-prod`。

禁止检查**开发环境**、**测试环境**的配置，一般文件命名包含 `-dev`、`-test`。

### 日志等级

生产配置中禁止将日志等级设置为：

```yaml
debug
```

包括根日志等级和包级日志等级。

发现后调整为符合现有项目约定的 `info`、`warn` 或更高等级。

### 连接信息

检查数据库、Redis、MQ 等连接配置。

重点检查：

- 数据库地址、用户名和密码。
- 多数据源中的 `master` 数据源。
- Redis 地址和认证信息。
- MQ 地址、用户名、密码、Access Key、Secret Key。
- 其他明显的连接凭据。

要求：

- 密码、密钥和令牌不得以明文硬编码。
- 多数据源中的 `master` 连接信息不得硬编码。
- 优先沿用项目已有的环境变量、配置中心或占位符规则。
- 没有现有规则时，使用语义明确的环境变量占位符。
- 不修改连接池、超时、重试等业务运行参数。

### 身份认证开关

以下配置禁止关闭：

```yaml
starfish.security.identityauth.enabled: false
```

以下情况例外：

- 配置项上方紧邻位置存在明确的关闭原因说明注释。
- 同一配置块中存在明确、可识别的关闭原因说明。

没有原因说明注释时，将其恢复为启用状态。

### CAS 忽略路径

禁止：

```yaml
cas.ignore: /*
```

或等效的全路径放行配置。

以下情况例外：

- 配置附近存在明确的关闭原因或全量放行原因说明注释。

没有原因说明注释时，移除全量放行，并保留其他明确配置的忽略路径。

## 依赖检查

依赖检查默认不执行。

仅当用户明确提出以下要求时执行：

- 检查无效依赖。
- 清理依赖。
- 检查 CVE。
- 修复依赖漏洞。
- 执行依赖合规检查。

### 无效依赖

检查 Maven 依赖声明：

- 移除确认未被源码、配置、插件或运行时机制使用的直接依赖。
- 对确认无须引入的传递依赖，可通过排除规则处理。
- 不因静态扫描结果直接删除反射、SPI、序列化、驱动或框架启动依赖。
- 修改后必须执行项目已有的编译或依赖检查命令。
- 无法确认安全性时不删除，只在汇总中说明。

### CVE

用户要求 CVE 检查时：

- 使用项目已有工具或用户指定工具。
- 仅处理用户要求范围内的漏洞。
- 优先升级到兼容的安全版本。
- 不进行与漏洞无关的依赖批量升级。
- 无法安全升级时说明漏洞、依赖和阻塞原因。

## 复检

完成修改后必须重新检查：

- 错误码格式、顺序和重复情况。
- 错误码枚举命名。
- 错误码翻译完整性。
- `suggestion` 中文句号。
- 错误日志是否包含错误码。
- 日志语言、脱敏、等级和标准写法。
- Logback 日志目录及文件名。
- 生产配置风险项。
- 无效导入和代码格式。
- 用户明确启用的依赖规则。

条件允许时执行项目已有的：

- 格式检查
- 编译检查
- 单元测试
- 配置检查
- 依赖检查

不得为解决与本次合规修改无关的构建失败而修改业务代码。

## 输出

处理完成后仅输出简短汇总，不展开逐条修改细节。

格式：

```text
合规处理完成

- 错误码：检查 X 项，修复 X 项，遗留 X 项
- 日志：检查 X 处，修复 X 处，遗留 X 项
- Logback：已检查 / 未发现配置
- 代码格式：清理 X 个导入，格式化 X 个文件
- 生产配置：检查 X 个文件，修复 X 项
- 依赖：未执行 / 检查 X 项，修复 X 项
- 复检：通过 / 存在 X 项未解决
```

存在未解决问题时，只补充：

```text
未解决：
- 文件路径：简短原因
```

禁止输出长篇分析、完整修改过程或与合规处理无关的建议。
