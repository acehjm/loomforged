# Source Code Analysis Guide

本规范只定义如何从源码中采集和验证业务事实。

分析阶段建立事实池，不编排 README 结构，不提前裁剪展示表达。目标是用尽量少的源码阅读，抓住能解释项目业务的入口、流程、规则、数据变化和外部交互。

分析过程中始终回答三个问题：

- 项目做什么？
- 为什么会得到这个业务结果？
- 源码依据是什么？

所有分析活动都应围绕这三个问题展开。

任何事实只有在能够解释业务目标、业务行为、业务结果或源码依据时，才值得继续深入分析；否则仅记录存在或停止分析。

如果时间或上下文有限，优先完成：

核心入口 -> 核心流程 -> 关键规则与边界 -> 数据流转 -> 外部交互

其它事实只在支撑业务理解时补充。

---

# 分析路径

1. 建立入口地图：快速识别接口、任务、消息、文件、命令、事件、SDK、用户操作和三方回调。
2. 选定核心链路：优先追踪能代表项目主要业务目标的入口和流程。
3. 解释业务结果：围绕核心链路确认哪些规则、过滤、边界、状态变化、数据变化、配置、外部交互或协作机制改变了业务结果。
4. 浅采辅助事实：对辅助入口、普通字段、普通端点、普通配置、普通读写和纯搬运逻辑只记录业务关系，不展开细节。
5. 标记不确定点：记录冲突、缺失、未实现、预留和无法确认的信息。

---

# 分析原则

- 准确优先于数量；不要为覆盖率而罗列所有文件、端点、字段或配置。
- 所有结论必须来自源码、配置、样例数据或可验证项目文件。
- 先判断业务相关性，再决定分析深度。
- 不用推测、常识或经验补充源码中不存在的信息。
- 不按技术类型预设项目；按业务入口、业务对象、业务规则和业务结果理解项目。
- API、字段、配置、数据库和协作机制只是业务事实来源，只有在影响业务判断、流程分支、数据变化、边界处理或结果去向时才深入分析。
- 无法帮助回答“项目做什么、结果如何产生、源码依据是什么”的内容，应降低分析深度或停止分析。
- 新增事实如果不会改变业务理解，只会增加实现细节，应停止继续分析。

---

# 采集深度

按影响程度控制分析成本：

| 类型 | 处理方式 |
| --- | --- |
| 核心入口、核心流程、核心业务对象 | 深入追踪到规则、数据变化、边界和结果 |
| 过滤、分流、状态变化、去重、增量、删除、外部调用 | 必须说明条件、依据、处理方式和结果 |
| 字段映射、配置、API、三方对接、数据库读写 | 只展开影响业务判断、流程分支、数据变化或结果去向的部分 |
| 普通字段搬运、普通保存、普通查询、普通端点、普通配置 | 简要记录或跳过，不做清单 |
| 纯技术结构、目录、依赖、构建、启动细节 | 只在帮助定位业务入口时使用，不展开分析 |

---

# 停止分析

分析目标是建立完整业务事实，而不是覆盖全部源码。

当以下信息已经能够确认时，应停止继续扩展分析：

- 已找到核心业务入口
- 已还原核心业务流程
- 已识别影响业务结果的规则、边界和数据变化
- 已确认重要外部交互
- 已能够解释业务如何从入口运行到结果
- 已能够用源码证据支撑关键结论

不要继续分析：

- 普通 CRUD
- 普通工具类
- 普通 DTO
- 普通 Mapper
- 普通配置
- 普通接口
- 普通数据库表结构
- 与业务无关的公共代码

避免为了提高覆盖率继续阅读大量源码。

---

# 事实记录格式

重要事实尽量记录：

- 事实内容：入口、对象、规则、字段、状态、配置、API、外部系统或协作机制。
- 来源依据：源码文件、配置、样例数据或脚本。
- 业务关系：关联入口、流程、业务对象、过滤、规则、边界、数据流或结果。
- 业务解释：该事实如何影响业务目标、业务行为或业务结果。
- 可信度：已确认、部分确认、冲突、缺失、未实现、预留或无法确认。

---

# 采集地图

进入陌生源码项目时，用以下线索建立分析地图：

- 项目清单：构建文件、包/模块配置、启动入口
- 业务入口：接口路由、命令、定时任务、消息消费、事件监听、文件导入、SDK 能力、用户操作入口、三方回调
- 配置来源：环境变量、配置文件、常量、特性开关、调度参数、外部地址、认证参数、默认值
- 数据边界：数据库访问、文件读写、缓存、队列、对象存储、第三方 API、导入导出对象
- 核心模型：领域对象、数据传输对象、状态字段、关键枚举、业务标识、关系字段
- 协作结构：任务编排、策略路由、适配器、事件机制、批处理队列、插件机制

采集地图只用于定位业务事实，不用于生成目录说明、依赖说明、表结构说明或源码结构说明。

# 事实采集范围

## 项目概况

优先确认：

- 项目名称、用途、所属业务域或问题域
- 项目类型、运行形态、主要组成部分
- 技术栈、服务端口、上下文路径、打包方式
- 能够解释业务差异的版本或发布标识

只采集能帮助建立整体认知的信息；不展开部署、运行、依赖和环境细节。

## 业务入口

识别可触发业务行为的入口，包括接口、任务、消息、文件、命令、事件、SDK、用户操作、三方回调和内部调度。

对业务相关入口优先确认：

- 入口名称、路径、命令、事件名、任务名或能力名
- 触发方式、触发条件、鉴权或前置条件
- 输入上下文中的关键业务数据
- 进入后的处理链路、业务目标和相关流程
- 成功、失败、跳过、异步、重试或补偿结果

非业务端点只作为候选入口标记，不展开。

## 核心业务与核心流程

先识别项目解决的核心业务问题，再追踪相对独立的核心流程。

对每个核心流程优先确认：

- 业务目标、触发入口、前置条件和输入来源
- 阶段性业务动作，参与的业务对象、标识、状态和关系
- 关键字段、状态、关系、数据变化和转换结果
- 过滤、分支、异常、跳过、重试、补偿和终止条件
- 数据最终写入、输出、返回、发送或同步到哪里
- 与其它核心流程的依赖或协作关系
- 必要源码依据和不确定点

流程分析围绕业务行为组织事实，同时保留必要源码依据用于核验。

## 过滤、规则与边界

过滤、分流和路由必须追踪到具体入口或流程阶段。

优先确认：

- 过滤、跳过、丢弃、失效、保留、分流或路由的条件、动作和结果去向
- 使用的字段、状态、配置、时间、权限、外部结果、历史数据、优先级和默认分支
- 状态判断、数据转换、去重、增量、删除、失效、归档、默认值、调度、权限、开关、灰度、策略选择等规则
- 失败、跳过、删除、重试、超时、限流、缓存、防重、补偿、预留、未实现等边界行为
- 空值、默认值、特殊字符、截断、大字段、文件、状态异常、外部异常、数据不完整、重复数据等特殊处理

只展开会改变流程、数据状态、业务结果或外部交互的规则和边界。

## 数据流、存储与数据库

数据库、缓存、队列和文件读写只是业务事实来源，不是分析目标。

优先确认：

- 业务对象保存在哪里
- 关键业务数据从哪里进入、如何变化、最终去向哪里
- 哪些状态、关系或结果会被持久化
- 哪些读写行为影响业务规则、边界判断或结果输出
- 数据库、缓存、队列、文件或对象存储如何参与业务流程

不追踪完整数据库结构、完整查询细节或普通 CRUD。

仅当表、字段、查询条件、状态值或读写行为会影响业务判断、流程分支、边界处理或结果去向时，才继续深入。

## 字段映射与数据转换

字段映射的价值在于解释业务，不在于完整追踪所有字段。

按业务对象、来源对象和目标对象追踪。

优先确认：

- 目标业务对象、来源对象、目标对象
- 影响业务判断、关系构建或结果去向的数据字段
- 转换、清洗、截断、格式化、默认值、特殊值、枚举转换、状态转换和空值处理
- 父子关系、组织关系、唯一标识、去重键、增量键、路由键
- 映射失败、字段缺失或格式异常时的处理方式

普通搬运字段不展开。

字段映射只有在影响过滤、分支、状态变化、外部调用、对象关系或结果去向时才深入追踪。

## 重要业务配置

配置的价值在于解释业务行为为什么不同，而不是记录部署参数。

只采集会改变业务行为、流程分支、数据范围、外部对接或运行结果的配置。

优先确认：

- 配置名称
- 默认值、当前值、示例值、取值范围或缺失时行为
- 配置控制的入口、流程、规则、过滤、边界或外部对接
- 不同取值对应的处理方式和结果

配置来源位置和读取方式只作为源码依据记录，不作为主要分析内容。

普通环境配置、启动参数和不影响业务行为的配置不展开。

## 重要 API 与外部对接

API 与外部对接的分析目标是解释业务如何被触发、协作和完成，而不是生成接口文档。

优先确认：

- API 是否参与业务入口、业务能力、规则触发点或关键流程节点
- API 或外部能力返回哪些会影响业务的数据
- 外部数据如何进入本系统、如何转换、如何过滤、如何写入或输出
- 外部系统、数据源、供应方、下游系统之间的先后、替代或兜底关系
- 外部调用失败、超时、数据缺失、重复或格式异常时如何影响业务
- 哪些认证、签名、分页、限流、超时、重试、幂等或回调约束会改变业务行为

协议细节、请求体、响应体、完整字段和普通端点不展开。

只有影响业务判断、流程分支、边界处理或结果去向时，才追踪 API 细节。

## 协作机制

协作机制的价值在于解释业务如何被分发、编排和选择，而不是总结系统架构。

如果源码中能识别任务编排、策略路由、适配器、事件机制、批处理队列、插件机制等结构，只在它们影响业务执行时分析。

优先确认：

- 机制是否影响业务分发、规则选择、任务编排或数据流转
- 机制影响哪些业务对象、流程阶段、外部对接或最终结果
- 异常、重试、跳过、补偿、幂等和并发处理是否改变业务结果

组件名称和源码结构只作为依据记录，不展开架构说明。

不要为了符合某种架构名词而总结设计模式。

---

# 追踪闭环

分析完成前，应能串起以下关键链路：

- 业务入口 -> 业务对象 -> 业务结果
- 请求、任务、消息、文件或三方数据 -> 关键业务对象
- 过滤条件 -> 被跳过、丢弃、失效、保留或分流的数据去向
- 关键字段 -> 规则判断、状态变化、外部调用或结果输出
- 业务规则 -> 源码判断条件、处理方式和结果
- 重要业务配置 -> 受控入口、流程、规则、边界或外部对接
- API 或三方 API -> 业务流程、请求响应和异常处理
- 数据库、缓存、队列或文件读写 -> 业务对象和结果去向

事实链断裂时，继续查找源码、配置或样例，并标记未确认部分。

如果关键链路已经能够解释业务结果，应停止继续扩展分析。

---

# 完成判断

完成分析时，应能基于源码证据回答：

- 项目做什么，业务从哪些入口进入，核心流程如何从入口走到结果？
- 为什么会产生这些业务结果？
- 哪些数据、对象、状态、关系、过滤、分流、路由、规则和边界会改变业务结果？
- 有哪些字段映射、数据转换、默认值、特殊值、异常处理和重要业务配置？
- 有哪些重要 API、三方 API、外部数据源、外部系统、数据库、缓存、队列、文件或对象存储参与业务？
- 哪些结论已确认，哪些仍不确定，每个结论的源码依据是什么？

如果无法基于源码证据回答上述问题，应继续追踪核心入口、流程、规则、数据流或外部交互，而不是进入 README 组织阶段。
