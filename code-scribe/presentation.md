# README Presentation Guide

本指南聚焦 README 如何展示；源码事实采集由 `analysis.md` 负责，质量验收由 `quality.md` 负责。

README 的目标是帮助工程师快速理解项目的业务、流程、规则，以及支撑业务运行的关键协作关系。

---

# 组织原则

始终遵循：

- 先整体，再细节。
- 先业务，再实现。
- 先主线，再补充。
- 相同主题集中组织。
- 重要内容优先展示。
- 流程和关系优先使用文本图或 ASCII 图表达。
- 不增加源码无法证明的背景、目的或设计原因。

README 围绕业务认知组织，避免按源码目录、模块、类、函数或技术类型铺陈。

根据项目特点合并、调整或省略章节，避免为了符合模板新增低价值内容。

README 应以尽可能少的内容帮助工程师建立完整业务认知。能够省略的内容应省略，能够融合的内容应融合，不为了完整而增加章节或篇幅。

如果两种表达方式都能准确表达业务，优先选择更容易阅读、更容易维护的一种，而不是信息量更多的一种。

---

# 信息优先级

优先回答：

- 项目做什么？
- 业务如何开始？
- 业务如何运行到结果？
- 什么规则、状态或边界影响业务结果？
- 数据如何流转、转换和输出？
- 哪些外部能力、API、配置或协作机制参与业务？

低价值信息适合省略、压缩或合并到相关业务说明中：

- 普通字段、普通端点、普通保存、普通查询、普通赋值。
- 工具类、公共组件、依赖库、目录结构、包结构和大量类职责介绍。
- 安装部署、运行说明、依赖清单、版本历史、运维文档。
- 完整 API 清单、API 参考、数据库表结构、数据库设计、附录。

数据库信息仅用于解释业务对象、规则、边界、映射或结果去向，不写成数据库设计文档。

---

# 内容组织

README 通常围绕以下主题组织：

- 项目概况
- 业务入口
- 核心业务流程
- 业务规则与边界
- 字段映射
- 业务配置
- 重要 API
- 三方 API / 外部对接
- 协作补充（如需要）

这些是主题，不是固定章节。

根据项目特点可合并、调整、改名或省略；源码不存在或对业务理解价值不大的主题无需补充。

## 项目概况

项目概况用于帮助读者快速建立整体认知。

通常包含：

- 项目名称
- 项目用途
- 项目类型
- 技术栈
- 当前版本
- 服务端口、上下文路径（如有）

适合使用统一表格表达，例如：

| 属性 | 说明 |
| ---- | ---- |
| 项目名称 | xxx |
| 项目用途 | xxx |
| 项目类型 | xxx |
| 技术栈 | Spring Boot + MyBatis + PostgreSQL + Quartz |
| 当前版本 | xxx |
| 服务端口 | xxx |

技术栈应展示影响项目整体定位的主要技术，不拆分数据库、缓存、调度、中间件等为独立条目；只有这些能力本身属于业务核心时才单独说明。

无法确认的信息直接省略，不写"未知"，不根据经验推断。

## 业务入口

业务入口用于说明业务从哪里触发。

适合使用表格表达。

优先展示真正具有业务含义的入口，避免按技术端点凑清单。

## 核心业务流程

核心业务流程是 README 主体。

其它信息围绕业务流程补充，避免抢占主线。

规则、映射、配置、API 和外部对接已能在流程中说清时，不重复展开；只有需要集中比较、复用或查阅时，再单独组织。

---

# 核心业务流程表达

核心业务流程负责说明业务如何运行，不负责罗列实现细节。

多个核心流程相对独立时分别展开；避免为了完整而强行画成一个大流程。

每个流程通常包含：

- 一句话说明流程目标。
- 文本图或 ASCII 图呈现主链路。
- 简短说明补充规则、过滤、状态变化、映射、外部调用、边界和结果。

流程内容应尽量覆盖：

- 入口与触发方式
- 关键业务动作
- 业务对象
- 判断、过滤、分流、跳过、失效
- 状态变化
- 数据变化
- 外部调用
- 最终结果

流程节点尽量同时体现：

- 对应源码锚点
- 业务动作
- 业务对象
- 关键规则或条件
- 处理结果

推荐采用：

> **源码锚点 + 自然语言描述**

例如：

```text
组织同步（OrgSyncTask.execute）

├── 规则：确保默认组织存在
│
├── 过滤：跳过已毕业班级
│
├── 映射：第三方组织编码 → 本地组织编码
│
├── 外部调用：同步组织到门禁平台
│
└── 结果：更新组织树
```

节点类型尽量明确，例如：

- 规则
- 判断
- 过滤
- 分流
- 映射
- 状态变化
- 外部调用
- 数据写入
- 结果

避免生成：

```
查询数据
↓

校验数据
↓

转换数据
↓

保存数据
```

这种缺乏业务含义的流程。

如果流程节点无法说明业务对象、规则或结果，应继续补充事实分析，而不是继续增加节点数量。

---

# 业务规则与边界

业务规则优先贴近对应业务流程表达。

如果规则已经影响核心流程，应先在流程中简要体现；本章节只补充流程中不便展开的规则细节，不重复流程内容。

适合集中整理：

- 跨多个流程复用的规则
- 过滤策略
- 分流策略
- 状态转换
- 删除策略
- 增量同步
- 重试
- 超时
- 特殊处理
- 边界情况

推荐优先使用对比表格。

规则应说明：

- 条件
- 处理方式
- 最终结果

避免只写：

- 存在过滤逻辑
- 包含重试机制

等空泛描述。

---

# 字段映射

字段映射用于解释业务对象之间的数据关系，不用于完整字段对照。

推荐按业务对象组织。

优先使用：

| 目标字段 | 来源系统 | 来源字段 | 转换规则 | 说明 |

多个来源写入同一业务对象时，每个来源单独一列；避免多个来源混写在同一单元格。

普通搬运字段可省略。

---

# 业务配置

仅展示影响业务行为的配置。

推荐使用：

| 配置项 | 默认值 | 控制内容 | 业务影响 |

配置确认优先级：

1. 源码默认值
2. 配置文件默认值
3. 外部部署配置

README 优先说明默认业务行为，而不是部署环境配置。

避免展示：

- 配置位置
- 部署步骤
- 环境搭建

---

# 重要 API

仅展示参与业务入口、业务规则或关键流程的 API。

推荐使用：

| Method | API | 业务作用 | 关联流程 | 关键说明 |

突出业务含义，而不是接口细节。

---

# 三方 API / 外部对接

按外部系统分组。

推荐使用：

| 系统 | Method | API | 调用场景 | 关键约束 |

突出：

- 外部系统承担什么业务作用
- 什么时候调用
- 为什么调用
- 对业务有什么影响

避免展示：

- 请求体
- 响应体
- 字段说明
- 输入输出
- 协议细节

---

# 协作补充

本章节仅在核心业务流程无法完整说明系统协作、数据流转或外部交互时使用。

优先在流程中说明：

- 数据从哪里进入
- 哪些组成部分参与处理
- 数据如何转换
- 数据最终去向
- 外部系统承担什么业务作用

如果上述内容已能说明，不单独增加本章节。

如确需补充，仅使用 3～5 条简短说明，解释：

- 协作机制如何影响业务流程
- 数据如何流转
- 外部系统如何参与业务
- 调度、策略、事件或批处理如何影响业务执行

不要还原系统架构。

不要生成：

- 分层架构图
- 模块图
- 依赖图
- 源码结构图

不要把依赖库、数据库驱动、中间件或基础设施误写成外部业务系统。

---

# 信息表达

表达方式服务于业务理解，不追求统一格式。

| 信息类型 | 推荐表达 |
| --- | --- |
| 项目概况 | 属性表 |
| 业务入口 | 表格 |
| 核心业务流程 | 文本图、ASCII 图 |
| 规则与边界 | 对比表格优先 |
| 字段映射 | 来源字段 → 目标字段矩阵 |
| 业务配置 | 配置项 + 默认值 + 控制内容 |
| 重要 API | API + 业务作用 |
| 三方 API / 外部对接 | 系统分组表 |
| 协作补充 | 简短说明；必要时使用轻量文本图 |

表格适合结构化信息，不适合承载核心业务流程。

核心业务流程始终优先使用文本图或 ASCII 图表达。
