# README Presentation Guide

本指南聚焦 README 如何展示；源码事实采集由 `analysis.md` 负责，质量验收由 `quality.md` 负责。

README 的目标是帮助工程师快速理解项目的业务、流程、规则，以及支撑业务运行的关键协作关系。

---

# 组织原则

始终遵循：

- 先整体，再细节
- 先业务，再实现
- 先主线，再补充
- 同类型信息必须先聚合，再表达（禁止拆分为多条同类重复节点）
- 重要内容优先展示
- 流程和关系优先使用文本图或 ASCII 图表达
- 不增加源码无法证明的背景、目的或设计原因

README 围绕业务认知组织，避免按源码目录、模块、类、函数或技术类型铺陈。

根据项目特点合并、调整或省略章节，避免为了模板完整性引入低价值内容。

README 应以尽可能少的内容帮助工程师建立完整业务认知。能够省略的内容应省略，能够融合的内容应融合。

---

# 信息优先级

优先回答：

- 项目做什么
- 业务如何开始
- 业务如何运行到结果
- 什么规则/状态/边界影响业务结果
- 数据如何流转、转换和输出
- 哪些外部能力、API、配置或协作机制参与业务

低价值信息：

- 普通字段、普通端点、普通 CRUD
- 工具类、公共组件、依赖库、目录结构
- 安装部署、运行说明、版本历史
- 完整 API 文档、数据库设计、附录

数据库仅用于解释业务，不作为结构说明。

# 内容组织

README 通常围绕以下主题组织：

- 项目概况
- 业务入口
- 核心业务流程
- 业务规则与边界
- 字段映射
- 业务配置
- 重要 API
- 三方 API / 外部对接
- 协作补充

这些是“主题”，不是强制章节。

# 🚨 核心规则：同类型信息必须聚合（强制）

任何同类型信息禁止逐条重复表达，必须先聚合再输出。

## ✔ 正确方式（聚合表达）

```text
规则：
├── 条件A
├── 条件B
└── 条件C
```

```text
映射：
├── 字段A
├── 字段B
└── 字段C
```

## ❌ 错误方式（碎片化）

```text
规则：A
规则：B
规则：C
```

## 聚合顺序建议

过滤 → 规则 → 映射 → 状态 → 写入 → 结果

避免交叉碎片化表达（规则/映射交替重复出现）。

# 核心业务流程

核心业务流程是 README 主体。

---

## 🚨 核心规则：流程必须结构化分组（禁止碎片化节点）

### ✔ 推荐结构

```text
人员同步（PersonSyncTask.execute）

├── 外部调用：分页拉取 Teacher / Student 数据
│
├── 过滤（已聚合）：
│   ├── 在职教职工（DQZTM="11"）
│   └── 在读学生（XSDQZTM ∈ {...}）
│
├── 映射（已聚合）：
│   ├── jgh → jobNo
│   ├── xm → name（截断 + 清洗）
│   └── xbm → GenderEnum
│
├── 规则（已聚合）：
│   ├── 姓名最多32字符
│   └── 证件类型固定 111
│
├── 数据写入：Disruptor → DB
│
└── 结果：同步完成
```

### ❌ 禁止结构

过滤：xxx
规则：xxx
映射：xxx
映射：xxx

### 节点约束

每个节点必须满足：

> 业务动作 + 业务对象 + 关键规则/条件 + 处理结果

无法满足 → 返回 analysis.md 补事实。

# 业务规则与边界

用于补充流程中无法展开的规则。

## ✔ 必须按类型聚合

过滤规则 / 分流规则 / 状态规则 / 并发规则 / 异常规则

## ✔ 每条规则必须包含

- 条件
- 处理方式
- 结果

---

# 字段映射

字段映射用于解释业务对象之间的数据关系。

## ✔ 必须按业务对象建模（矩阵）

| 目标字段 | 来源系统 | 来源A字段 | 来源B字段 | 转换规则 | 说明 |

## 约束

- 多来源必须拆列
- 同一目标字段禁止重复行碎片化
- 固定值必须显式标注
- 缺失用 “—”

# 最终原则

README 的目标不是完整，而是快速建立业务认知。
所有结构必须服务：可读性 / 理解速度 / 信息密度 / 稳定性
