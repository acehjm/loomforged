# README Review Guide

本指南用于判断 README 是否可交付。

它不重复 `presentation.md` 的写作方式，也不要求 README 填满所有信息项；只评审 README 是否基于源码事实，真正帮助工程师理解项目业务。

评审时优先判断：

- 读者能否理解项目做什么
- 读者能否理解业务从哪里进入
- 读者能否理解核心流程如何运行到结果
- 读者能否理解为什么会产生这些业务结果
- 读者能否理解哪些规则、边界、数据变化或外部协作会影响业务结果
- README 是否克制、准确、可读、可维护

---

# 必须返工项

出现以下任一问题，直接返工：

- 核心业务、业务入口或核心业务流程缺失，导致读者无法理解项目做什么、从哪里进入、如何运行到结果。
- 存在核心业务流程，但缺少文本图或 ASCII 图，或多个独立流程被强行合并导致主线看不清。
- 过滤、规则、边界、状态变化、关键映射或关键数据变化被抽掉，导致无法理解业务如何运行。
- 流程节点只有“校验数据”“转换数据”“保存数据”“调用接口”等泛化动作。
- 流程节点缺少业务对象、关键规则或处理结果，导致文本图只有动作堆叠而无法解释业务结果。
- 核心结论无法从源码入口、规则、配置、数据处理或外部调用中验证。
- 使用推测、常识或经验补充源码中不存在的信息。
- README 漂移成源码目录说明、类函数说明、数据库设计、API 参考、安装部署、依赖清单、版本说明、运维文档或附录集合。
- README 将协作补充写成架构图、模块图、依赖图或源码结构图，导致技术结构噪音压过业务流程。
- 三方 API / 外部对接展开入参、出参、请求体、响应体、返回字段、关键输入或输出内容。

---

# 信息完整性

检查 README 是否覆盖源码中真正影响业务理解的信息。

重点判断：

- 项目概况是否足以建立整体认知。
- 业务入口是否说明业务从哪里触发。
- 核心业务流程是否说明业务如何从入口运行到结果。
- 业务规则与边界是否说明改变业务结果的条件、处理方式和结果。
- 数据流转是否说明关键数据如何进入、转换、写入、输出或同步。
- 字段映射是否覆盖影响业务判断、关系、状态、去重、路由或结果去向的映射。
- 业务配置是否覆盖影响流程、规则、数据范围、外部对接或结果的配置。
- 业务配置是否优先体现源码默认值或配置文件默认值，而不是以部署环境配置替代默认业务行为。
- 重要 API 是否覆盖参与业务入口、规则判断或关键流程的 API。
- 三方 API / 外部对接是否覆盖参与业务协作的外部系统、API 路径或能力、调用场景和约束。
- 协作机制是否覆盖影响业务分发、规则选择、任务编排或数据流转的关键机制。

这些信息不是固定清单。

源码不存在、业务无关、对理解没有帮助，或已在其它位置完整表达的信息，不应为了完整而补充。

---

# 表达质量

检查 README 的表达是否帮助理解业务，而不是制造阅读负担。

重点判断：

- 核心流程是否讲清“业务动作 + 业务对象 + 关键规则/条件 + 处理结果”。
- 流程节点是否尽量体现“源码锚点 + 自然语言描述”，并明确规则、过滤、判断、映射、状态变化、外部调用、结果等节点类型。
- 流程表达方式是否适合项目特点，而不是为了画图或列步骤而增加内容。
- 图、表和文字是否互补，而不是重复表达同一信息。
- 结构化信息是否合理使用表格，核心流程是否没有被表格替代。
- API 是否突出业务含义，三方 API / 外部对接是否突出业务协作。
- 代码锚点是否帮助定位源码，而不是替代业务描述。
- 补充说明是否简短、必要，并服务于核心业务理解。

---

# 信息取舍

检查 README 是否做了有效取舍。

重点判断：

- 是否保留了真正影响业务理解的信息。
- 是否删除或压缩了低价值实现细节。
- 是否没有为了完整而增加章节、清单或表格。
- 是否没有平均介绍所有模块、端点、字段、配置或数据库对象。
- 是否避免让补充内容超过核心业务流程的篇幅。
- 已在流程中完整表达的内容，是否没有在规则、映射、API 或配置中再次重复展开。
- 规则章节是否只补充流程中不便展开的信息。
- 协作补充是否保持简短，仅用于补充核心流程无法说明的协作、数据流或外部交互，而不是展开系统架构。

如果 README 内容更多，但并没有让业务更容易理解，应视为质量下降。

---

# 阅读体验

检查 README 是否适合人类工程师快速阅读。

重点判断：

- 阅读顺序是否自然，能否先建立整体认知，再理解关键细节。
- 核心业务流程是否是全文主线。
- 重点是否突出，是否能快速定位入口、流程、规则、边界和外部协作。
- 图、表、文字比例是否合理。
- 是否存在明显重复、过度嵌套、字段级流水账或大段低密度说明。
- 是否以尽可能少的内容帮助读者建立完整业务认知。

---

# 最终判断

如果目标读者仅阅读 README，而无需先阅读大量源码，即可回答以下问题，则认为 README 达到交付质量：

- 这个项目做什么？
- 业务从哪里进入？
- 核心业务流程如何运行到结果，为什么会产生这些业务结果？
- 哪些规则、状态、过滤、边界或映射会影响业务结果？
- 数据如何流转、转换、写入、输出或同步？
- 哪些重要 API、三方 API、外部系统、配置或协作机制参与业务？

如果上述问题中仍有明显无法回答的内容，应继续分析源码并完善 README，而不是直接交付。
